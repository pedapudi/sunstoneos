# Several trusted NPU models as concurrent sessions

The session runtime is **implemented** and passes FreeRTOS emulator checks on two
QEMU cores with a register model in place of the NPU. It runs up to eight
compiled models on the one NPU, each owned by its own client task, and starts
their jobs one at a time in round-robin order. No board image links it yet,
and physical execution, memory confinement and numerical inference on the
NPU remain unqualified.

The interface is [npu_session.h](../include/npu_session.h), implemented in
[npu_session.c](../drivers/npu/npu_session.c). It uses the
[general assembly plan](nbg-assembly.md#a-general-plan-covers-several-tensors),
the [memory policy's session groups](npu-memory.md), the
[shared service mode](npu-service.md#shared-mode-gives-each-client-its-own-session)
and the existing startup adapter. The reservation constructor is
[npu_session_reserved.c](../platform/a733/npu_session_reserved.c). The
[single-model registration](npu-convolution.md) remains the path of the
existing board images and is unchanged.

## A privileged catalogue admits the models

Executable models come only from the build-time catalogue in
[npu_session_models.inc](../drivers/npu/npu_session_models.inc), generated by
[npu-session-catalogue.py](../tools/npu-session-catalogue.py) from
[npu-session-models.json](../tools/npu-session-models.json). Each entry fixes
the model's size and SHA-256 together with its tensor sizes and the operation,
relocation and command-body counts that the native assembler derives. The JSON
record adds the decoded tensor descriptors, reference input and output
identities and the producing compiler step. A caller cannot add an entry with
a hash, and there is no runtime upload; adding a model means reviewing its
compiler output and regenerating the table. The catalogue holds:

| Model | Inputs | Outputs | Operations | Model bytes |
| --- | --- | --- | ---: | ---: |
| 8×8 convolution (`conv8`) | one UINT8, 192 bytes | one UINT8, 72 bytes | 1 | 1,928 |
| Two convolutions (`dual-u8`) | UINT8, 192 and 36 bytes | UINT8, 72 and 32 bytes | 2 | 2,912 |
| Same graph, INT8 per-channel (`dual-i8`) | INT8, 192 and 36 bytes | INT8, 72 and 32 bytes | 2 | 2,912 |
| Published ShuffleNetV2 | one UINT8, 150,528 bytes | one UINT8, 2 bytes | 125 | 964,224 |
| mimus encoder query projection (`mimus-linear-q`) | INT16 8×176, 2,816 bytes | INT16 8×176, 2,816 bytes | 3 | 34,248 |

The two-convolution graphs come from [npu-dual-pipeline.sh](../tools/npu-dual-pipeline.sh)
and the mimus layer from the [mimus layer study](npu-mimus-linear.md); both use
the pinned compiler described in [npu-compiler.md](npu-compiler.md).
ShuffleNetV2 is the published SDK example and needs a 1,092,352-byte external
working pool. The other graphs keep intermediates in internal SRAM.

Each catalogue model also passes the decoder, checksum and assembler policy,
which are independent of the hash. Hash identity does not establish the
device's complete access extents; the reviewed compiler output and effective
NPU page-table confinement remain the admission basis, as for the single-model
registration.

## One parent allocation holds every model

`npu_session_requirements` computes the size of one parent allocation from
the selected models' plans. `npu_session_prepare` then fills it in this order:
the private model copies, one 512 KiB bootstrap stream, each model's
descriptors, coefficients, working pool, 512 KiB command stream, inputs and
outputs, and finally the NPU page tables. Every allocation is 4 KiB aligned.
Device addresses start at `0x10000000` and leave one unmapped 4 KiB page after
every allocation, so an access that runs past an allocation faults in the NPU
MMU instead of reaching the next one. The page tables take 4 KiB plus 16 KiB
for every 16 MiB of device addresses that the allocations touch.

The three small models need 2,195,456 bytes in 20 allocations; all five
catalogue models need 6,459,392 bytes in 31 allocations. The memory policy
accepts at most 64 allocations, so a selection can also be refused for that
reason.

`a733_npu_session_reserve` takes that exact size from the platform pool that
`a733_memory_reservations_init` returns. In the default profile that pool is
2 MiB of image RAM. In the extended cached profile it is the boot-validated
write-back DDR reservation from `0x48000000` to `0x78000000`, so selections
larger than the image-RAM window, such as all five catalogue models, fit there.
The lease becomes DEVICE-owned for the session's lifetime; a preparation
failure after admission marks it RETAINED, and a pool that is too small is
refused before anything is allocated.

## Preparation authenticates and assembles from private copies

Preparation copies every model into the parent allocation first. It hashes
each copy with the shared SHA-256 helper, finds its catalogue entry, decodes
and plans it, and checks the plan against the entry. It then builds the native
memory policy over all allocations, assigns each model's allocations to
session group model+1, assembles each model into its allocations, writes the
bootstrap stream and records digests. Descriptors and coefficients are
CONSTANT; inputs are READ; outputs and the working pool are WRITE.

The integrity checks follow the single-model registration. The bootstrap
publication, service activation, startup polling and stop polling check every
model copy, every descriptor and coefficient allocation and every command
stream, including the bootstrap stream. A job publication checks the
submitting model's descriptors, coefficients and command stream. Each command
stream is checked as a digest of its payload plus a check that every later
8-byte unit is an END pair. Any failure after admission is terminal: the
runtime refuses every further call and retains the parent allocation.

Jobs of different models never overlap on the controller, and each model's
command stream relies only on the shared bootstrap state. Internal SRAM
therefore holds one job's intermediates at a time, and its ownership
requirements are those of the single-model application.

## Startup, interrupts and clients

`npu_session_bind` takes an initialized [startup sequencer](npu-startup.md)
with its bootstrap task bound. It constructs the deferred service in shared
mode with the private backend, the MMU image and the command table (the
bootstrap, then one command per model), and binds client task *i* to model
*i* with permission for its command only. The service's activation callback
compares the service's copy of that metadata once and then asks the startup
whether it is READY. `npu_session_bind_irq` optionally binds interrupt
completion before scheduling. `npu_session_startup_poll` and
`npu_session_stop_poll` call the sequencer's step and stop functions on the
startup task; the stop poll requires every model's copied successful CLOSE.

Each client uses `npu_session_send` and `npu_session_collect` with the shared
service's operations. SUBMIT takes one span per input tensor, each exactly that
tensor's logical size, clears the model's working pool and copies the inputs
while the model has no job. Other models' completions cannot invalidate those
writes because they belong to a different session group. WAIT holds until the
model's job is DONE; `npu_session_output` copies one output tensor before
REAP. `npu_session_tensor` returns the decoded descriptor of any input or
output, including its scale and zero point. A model's CLOSE ends its session
permanently. A service fault or an unexpected reply retains every model.

## Emulator checks

[npu-session.py](../checks/npu-session.py) compiles
[npu-session.c](../checks/npu-session.c), the runtime and its dependencies with
the npu-service-model target's flags and link line, embeds catalogue models
after verifying their hashes, and runs QEMU with two Cortex-A55 cores:

```sh
checks/npu-session.py BUILD_DIRECTORY NEW_OUTPUT_DIRECTORY --mode session --artifacts ARTIFACTS.json
checks/npu-session.py BUILD_DIRECTORY NEW_OUTPUT_DIRECTORY --mode reserved --artifacts ARTIFACTS.json
```

`ARTIFACTS.json` maps each catalogue name to its model, input and reference
files. The register model never interprets commands. When a job completes it
reads each assembled descriptor through the published NPU page tables and
writes every model output from the input that descriptor names, or from zero
when the descriptor reads intermediate memory. Each client checks its outputs
against that rule, so a wrong relocation, mapping or session group changes
the result. Changing the assembler so that input and output relocations
always name tensor 0 makes both nominal session cases fail.

| Mode and case | Result |
| --- | --- |
| Session, case 0 | Three models, three jobs each, polled completion. One job completes per credit, granted only while every model has a job queued; the start order repeats with period three. Outputs of single- and two-tensor graphs match. Startup polling, CLOSE of every model and the stop poll pass. |
| Session, case 1 | The same models complete through the interrupt path: ten notified completions, one bootstrap and nine jobs, then the interrupt stop. |
| Session, case 2 | A coefficient byte of one model changes after admission. Its job publication is refused before any cache maintenance or trigger; the controller faults with a memory fault and every client call is then refused. |
| Reserved, case 0 | All five catalogue models from one 6,459,392-byte reservation in a 48 MiB pool, larger than the 4 MiB image-RAM window. ShuffleNetV2's working pool is all zero, read through the NPU tables, at the start of every job, after the previous job filled it. |
| Reserved, case 3 | A 4 MiB pool cannot hold the parent: the reservation is refused and every pool slot stays free. |

Before scheduling, the checks also refuse these preparation inputs: a model
whose bytes differ from its catalogue entry, zero or nine models, a parent of
the wrong size, a wrong register address, a missing fatal callback and a
second preparation. Binding refuses duplicate client tasks, the startup task
as a client and an interrupt binding before the service exists. Clients are refused for wrong input counts or sizes,
inputs inside the parent allocation, another model's index, output before
DONE, a wrong output size and an OPEN after CLOSE. Allocations are checked
for guard pages, the parent bounds and their session groups.

Every case passed. Each session case passed five consecutive QEMU runs of
the same ELF, and reserved case 0 three.
Results, the generated fixture header, the ELF and its build commands are
under `~/.cache/sunstoneos/build/audit-npu-runtime/evidence/session/` and
`.../reserved/`. The modeled device writes do not establish NPU arithmetic,
cache visibility on the board, interrupt delivery or confinement.

## Remaining work

- A board application that links the session runtime. The supervised board
  image links the single-slot runtime instead
  ([designs/npu-board.md](designs/npu-board.md)). The single-core NPU images
  construct their providers in `apps/npu-convolution/native.c`, which is
  written for the single-model registration; an image that runs the session
  runtime needs that file to select it.
- Physical qualification of concurrent jobs, interrupt completion and the
  integrity and retention behavior on the board.
- Models outside the catalogue's operation profile: tensor-processor, shader
  and software operations and tensor types other than affine 8- and 16-bit
  integers.
- 64 KiB NPU pages for large allocations, which would need 64 KiB-aligned
  placement and changes to the memory policy's table validation; 4 KiB pages
  are correct at any size.
