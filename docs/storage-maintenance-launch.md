# Native storage maintenance launch

The dedicated maintenance image runs the actual storage, PMIC and USB tasks on
the cached eight-core FreeRTOS port. It accepts one immutable storage grant and
stops activity at that grant’s absolute deadline. A separate watchdog owner may
reload the already armed hardware only after verified storage progress and the
corresponding USB response and subsequent request.

This path is implemented but not physically qualified. Launch requires actual
independent reset, memory, controller, supply, card and SRAM preservation evidence
for the current board instance. No qualifying records are generated by preparation.
The existing bounded diagnostics and sealed observer use their original contracts.

The image target is `sunstone-a733-storage-maintenance`, available in the main
build or configured separately from `platform/a733-storage-maintenance`.
It uses the existing cached CPU, interrupt
and kernel implementation. Private patches reserve the session page, publish it
before cache adoption, admit the three native tasks at EL1 and revoke maintenance
on a runtime exit. The interrupt handler uses the grant deadline copied through
the boot contract; it does not renew a diagnostic timer.

## One session binds the grant and watchdog owner

The 704-byte little-endian session occupies a dedicated NOLOAD page at
`0x41f00000`. File-backed ELF bytes cannot overlap it. The linker keeps ordinary
mutable allocations below that page. The host uploads the page separately and
verifies its complete readback before execution.

`platform/a733-storage-maintenance/session.h` defines the wire offsets. The
existing 256-byte storage grant begins at offset 160 without translation or
additional authorization fields. The session also binds the epoch, generation,
boot lease, final ELF digest, physical recovery digest, qualified watchdog bounds,
RTC source snapshots and native pin, clock and supply configuration.

The 32-bit word at offset 456 selects the SD bus profile for the MMC platform:
0 for one-bit 400 kHz operation, 1 for four-bit default speed and 2 for
four-bit high speed. The optional `mmc_sd_profile` configuration key sets it
and defaults to 0. The launcher and the native decoder refuse any other value,
a nonzero profile for eMMC and nonzero bytes in the reserved range 460..487.
The native platform refuses a pin route that does not match the profile:
profiles 1 and 2 require mux 2 on PF0–PF5.

The initial reload observations at offsets 640 and 648 are zero in uploaded
bytes. The ARM launcher records the physical counter immediately before and
after the initial hardware arm/reload sequence. It requires a span shorter than
one millisecond and publishes the session magic last. The boot contract is then
published with the same epoch, generation, lease and grant nonce.

All runtime times are absolute microseconds from the continuous 24 MHz physical
counter. The boot contract uses ticks. Multiplication by 24 must fit 64 bits.
The contract’s startup bound is one second after the initial arm observation.
Its interrupt cutoff is the grant deadline; its reset bound is the qualified
absolute `reset_by_us` value. The grant must leave the qualified maximum recovery
interval before that reset bound.

The primary EL1 bootstrap decodes the immutable session into the actual native
constructor inputs and the watchdog transfer. It derives provider startup bounds
from the earliest qualified reload expiry, guard and one-second operation reserve.
The transfer references the constructor’s copied grant. No uploaded C pointer is
accepted. The native constructor creates the actual tasks and binds their handles
to the single watchdog owner before starting the scheduler.

Set `mmc_sd_profile` to `2` in the admitted launch configuration to use
64-sector DMA backup reads; the default profile zero retains eight-sector PIO.
SD profile two uses a private descriptor chain in the existing noncacheable
pool at `0x41c00000–0x41e00000`. The image reserves that 2 MiB block and uses
528 bytes for descriptors. Bootstrap rejects any supplied DMA pointer before
selecting this array. Admission checks every descriptor and readback page for
identity mapping, normal memory attributes and inner shareability; the cached
image's existing coherence admission remains mandatory. The permanent 32 KiB
readback buffer owns complete 64-byte cache lines, separate from input and
service state. The existing cache adapter cleans its exact borrowed range
before DMA and invalidates it only after the core proves descriptor completion
and controller drain. Failed transfers retain the range, descriptors and leases.
Writes remain one-sector PIO, with DMA disabled and CPU FIFO selected before
CMD24. See [the backup protocol](storage-update.md) for batching and memory costs.

Runtime exits revoke subsequent feeds. Fatal exceptions use the existing atomic
lease after validating the current EL3 translation and every core’s canonical
translation record. They select a reserved Secure Device stack before calling C.
An early fault without those prerequisites parks without accessing ordinary RAM.
Atomic bootstrap publication cannot overwrite an earlier revocation. A committed
reload cannot be retracted.
A fault that prevents runtime execution relies on independently qualified hardware
expiry and the absolute session bound. Neither source inspection nor register
readback proves that the watchdog counter progresses or resets a stalled fabric.

## The host retains the protected storage artifacts

`tools/check-a733-storage-launch.py prepare` reads an actual runtime ELF and its
matching manifest, a configuration record and a protected storage directory.
It records the exact image, grant, candidate, backup and configuration identities.
Preparation compiles the separate SRAM launcher and performs no board operations.

Writer directories come from `tools/storage-update.py prepare`. The launcher
reopens and verifies their sealed `grant.bin`, backup, candidate and ordered
commitment chain before upload. It holds the protected directory lock throughout
connected application of the grant.

A first read-only capture requires an already identified card and an exact
SunstoneOS-owned range. `prepare-capture` consumes that identification, the existing
allocation and recovery evidence, and a complete read-only grant. It preserves
these inputs in a protected directory. It cannot discover or invent a card identity.

The distinct SRAM reservations are:

| Purpose | Physical range |
| --- | --- |
| Launcher code | `0x52000..0x54000` |
| Request | `0x54000..0x54080` |
| Report | `0x54100..0x54180` |
| Stack | `0x55000..0x56000` |
| Existing scratch preservation | `0x71000..0x71080` |

Physical admission must cover preservation and restoration of every listed range.
The host saves those bytes before upload, uses immutable sealed transfer files,
verifies readbacks and issues exactly one execution request. A matching refusal
from the original ROM instance permits restoration before any device mutation.
Architectural refusal or failure after mutation may park without an armed watchdog;
the coordinator retains ownership and uses the separately qualified recovery path.

The live sequence waits for the distinct maintenance USB device, then invokes the
existing `USBExchange`, `Client`, `backup` or `apply` implementation. USB revision
`0x0102`, product, serial number and current instance must match. Transport failure
permanently ends communication and quarantines that instance. No reconnect retry
resumes a partially completed storage session.

The active USB task follows the [shared USB0 burst policy](../apps/board/usb0_service.h):
at most 200 microseconds or 64 passes, with up to 125 microseconds of polling
after recent progress, then a one-tick fairness delay. An idle first pass ends
the burst immediately. Maintenance polls the controller before TinyUSB
and detects changes in received, queued and completed bytes and request sequence,
as well as pending events and newly armed IN transfers. This detects completion
even when a pass refills the FIFO to its previous level. Each burst starts with
fresh progress state. Provider waits inside a pass still yield; their elapsed
time exhausts the burst budget when the pass returns. One already-started pass
may finish beyond the time limit. The checked counter must remain monotonic and
within the original grant deadline; failure retains the session. No burst
extends an operation or watchdog deadline, and only the final completed IN
publishes response completion.

The storage implementation fsyncs its completion receipt before the launcher
begins observing ROM return. A distinct accessible ROM response is recorded
separately. It does not establish the reset cause, storage durability after power
loss or bootability of written bytes.

## Selective validation

The connected check builds the actual maintenance image and exercises the new
launcher/session boundaries and protected host lifecycle. Its decoder cases
also confirm that profile 2 reaches the decoded MMC configuration and that a
profile of 3, a nonzero reserved byte and an eMMC profile refuse. The recorded composition
passed nine ARM launcher cases, nine linked AArch64 admission, decoder and fatal
exception cases, and the protected host backup lifecycle. The runtime dependency
manifest matches the compiled source and headers. The build log preserves the
initial include-selection and missing-adapter link corrections; successful objects
were reused during incremental completion. Existing cached scheduler,
storage command/readback and watchdog progress evidence remains applicable to
unchanged dependencies. The complete image rebuilds every clock-token consumer
against one shared clock ABI.

Evidence is preserved under
`~/.cache/sunstoneos/evidence/storage-maintenance-20261017/`.
`final/handoff.json` identifies the linked image, compiled dependencies and
focused results. The main build configuration passes; `central/root-reconcile.json`
records matching integrated source and saved artifact identities. Configuration
and source comparison reused the saved ELF without another build or runtime check.

Instruction models do not implement A733 cache coherence, peripheral timing,
physical USB enumeration or independent recovery. Those remain physical prerequisites.

The focused `checks/storage-maintenance-usb-burst.py` comparison executes the
burst loop and the former one-pass-per-tick loop with the same modeled 2 KiB
FIFO, 512-byte endpoint and host turnaround. A 32,840-byte framed response takes
8 scheduler ticks rather than 66, and a one-packet response takes one rather
than two. Idle remains one
pass per tick. Delayed or abandoned hosts, counter stalls and failures, expiry,
and provider loss or waiting exercise the burst and retention boundaries.
These counts establish scheduling behavior under the model, not physical
throughput. The existing DMA and storage-command evidence is reused.
