# Native reservations for the fixed GPU compute job

The [compute constructor](../platform/a733/gpu_compute_reserved.c) allocates the
buffers and GPU page tables required by the existing fixed compute service.
It runs the actual VM, program, context, job and MIPS builders, then binds the
result to the reserved firmware instance. It supplies no power, physical core
observation, isolation or drain provider. Physical computation remains unqualified.

## Three complete parents remain owned for the boot lifetime

The constructor requires the [reserved firmware instance](gpu-reserved.md),
an uninitialized GPU service and private static session storage. Initialize the
session once and serialize construction with every pool operation before the
scheduler starts. The firmware must remain stopped and unattached during
preparation. A retained singleton owns the fixed compute firmware address ranges,
including after partial construction failure.

The constructor reserves 88 write-back pages for program and payload storage,
six uncached pages for firmware objects, and a separate write-back parent for
GPU page tables. It obtains the table size from the actual VM planner using
the admitted mappings. The six firmware objects hold the context, register
state, command control, command ring, VM record and timeline word.

Each acquired parent becomes device-owned before initialization. Any later
failure permanently retains all acquired parents. Children cannot be released;
completion and service shutdown do not return these allocations to the pool.
Free-list growth, context disposal and additional jobs remain separate work.

The fixed layout uses 12 GPU table pages: one root, three directories and eight
leaf tables. Together with the NPU parent, one entropy page and the firmware
constructor, it occupies 400 of 512 write-back pages and 51 of 512 uncached
pages. This leaves 448 KiB write-back and 1,844 KiB uncached capacity. Those
figures describe these fixed allocations, not a budget for all board hardware.

## Heap addresses match the actual firmware initialization

The compute program sequencer uses heap base `0xda00000000`; the shader core
uses `0xe000000000`. Each heap spans 4 GiB. General data uses the 128 GiB heap
at `0x8000000000`. These are GPU virtual ranges, not additional physical RAM.
They match the pinned native heap profile and the actual firmware initialization
records. The [heap definitions](https://github.com/orangepi-xunlong/linux-orangepi/blob/2ac08e8c7cdc28abbdc5c9a9dd812f887ae9c79f/bsp/drivers/gpu/imagination/pvr_rogue_heap_config.h)
and [firmware initialization](https://github.com/orangepi-xunlong/linux-orangepi/blob/2ac08e8c7cdc28abbdc5c9a9dd812f887ae9c79f/bsp/drivers/gpu/imagination/pvr_fw.c)
are preserved with the evidence.

Admission checks the sequencer and shader heap bases in the actual system
initialization buffer. Relative program offsets therefore agree with the bases
passed to firmware. Full general addresses remain present in the generated
command stream. The MIPS builder includes all 19 original firmware resources
and all six compute objects before service binding.

## Local admission checks retained ownership and build provenance

The constructor supplies bounded admission callbacks that verify real pool
leases, generations, complete extents and native CPU translations. They also
verify canonical descriptors, all 88 workload mappings, exact planner output,
heap bases and the constructor's build state. A copied binding, stale lease,
changed mapping or conflicting heap configuration refuses admission.

Session metadata, table bytes and generated programs remain private and
immutable until their documented service ownership transitions. Build state
records successful calls to the actual builders; later admission does not
reconstruct every generated byte. Ordinary task mappings provide cooperative
ownership and do not isolate hostile writers. Boot admission must still exclude
external users and alternate CPU mappings.

Use the existing native backend and service startup after construction.
The service requires freshly observed single-core capability after power
activation and before firmware startup and computation. Memory reservation
cannot establish that capability or physical GPU visibility.

## Focused verification checks construction and refusal

The [instruction fixture](../checks/gpu-compute-reserved.py) executes native
translation instructions and the actual builders. One mode checks complete
construction, service binding, retained ownership and mutation refusal. The
other leaves the write-back pool one page short of the planner's table request
and checks retention of both already-acquired parents.

NPU and entropy occupancy use their complete retained extents. Their existing
preparation checks are reused. The fixture executes no accelerator command,
models no successful physical completion, and performs no benchmark. Existing
boot-layout, firmware lifecycle and numerical checks are not replayed.

Both selected modes passed. The executed base image has SHA-256
`a5548ee822938716ce43bc38d7862dae0a684dea138efc9a31919dc1f105f306`.
Evidence, dependency snapshots and the selected executable identities are in
`~/.cache/sunstoneos/evidence/gpu-compute-reserved-20261016/batch/`.
