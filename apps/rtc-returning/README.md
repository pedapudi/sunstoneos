The returning RTC image performs two coherent calendar reads using the production driver.

One FreeRTOS task adopts an existing valid calendar through the explicit read-only driver API. It accepts external 32768 Hz or normal internal RC selection; calibrated RC selection is explicitly refused until its readiness contract is established. Before accessing RTC registers, it verifies that R_CCU gate/reset-release bits 0 and 16 are already set. It also requires interrupt 228 disabled, inactive and unpending. It refuses missing prerequisites without enabling the bus, releasing reset or acknowledging events. Its write callback rejects every RTC store.

The task waits at least 1.1 seconds between readings and accepts one or two calendar seconds of observed advancement. Normal RC adoption makes no 1 Hz or accuracy claim. Other actual deltas produce an honest negative progression result while retaining observed calendar/source fields. Counter initialization requires the existing 24 MHz architectural counter. A 1.5-second client deadline starts before gate, interrupt and driver work. The task yields during its wait, preserving scheduler interrupts and the accepted monitor's unchanged two-second recovery deadline. It reports source state, saved alarm target, decoded calendar readings and counter timestamps through the existing RAM log, then publishes an operation outcome and calls platform_exit. It does not initialize native USB.

The common completion marker reports normal read-only termination, including controlled refusal. `RTC_READ_OUTCOME` is 0 for `COHERENT_SUCCESS` and 1 for `CONTROLLED_NEGATIVE`. Only outcome 0 contains the functional PASS marker. The exact `RTC_READ_REASON`, step and driver state remain in the report. `RTC_READ_OBSERVED_MASK` identifies fields actually sampled: bit 0 bus, bit 1 source control, bit 2 source status, bit 3 calendar day, bit 4 calendar HMS, bit 5 RC prescaler, bit 6 calibration register and bit 7 oscillator control. `RTC_READ_SOURCE_KIND` is 0 before successful source adoption, 1 for external and 2 for normal RC. Fields without their presence bit carry no observation. Observations are captured from existing reads without additional register access.

A normal controlled refusal exits with status 0 so the unchanged runner can recognize normal monitor cleanup and ROM return. RTC operation success additionally requires outcome 0 and valid readings; runner completion alone does not qualify the RTC. An unexpected call to the refusing write callback is an invariant failure: status 1 without the common completion marker. Actual panic and monitor timeout behavior remain unchanged.

Normal RC source adoption reads calibration selection at RTC+0x0c, prescaler at +0x08 and RC enable at +0x160 after the existing bus preflight. The unchanged platform identity-maps this peripheral range as Device memory. Only source-control fields, prescaler low five bits, calibration-selection bit 0 and RC-enable bit 0 are required stable. Unused calibration-result and shared DCXO fields remain observations; no oscillator, divider, source or calendar register is written.

The read-only driver instance retains `ops.write=NULL`. Its arm, IRQ acknowledgment and finish entry points reject mutation. Passing those instance ops into the existing source/calendar initialization and runtime setting APIs refuses before I/O. Independently retained caller raw ops remain separate privileged authority. Existing strict open and full RTC modes keep their external-source policy; normal-RC alarms, writes, full service, calibration and retention remain future capability work.
